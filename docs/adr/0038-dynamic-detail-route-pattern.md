# Dynamic Detail Route Pattern

Date: 2026-04-25

## Status

Accepted

## Context

The project now ships two dynamic detail routes:

- `/success-stories/[slug]` — landed earlier under
  [ADR-0033](_archive/0033-inline-first-page-composition.md) (since superseded
  by [ADR-0034](0034-extract-first-for-ai-assisted-development.md)). The route
  reads `successStories` data, filters with the `hasDetailPage` type guard, and
  renders a long-form composition gated behind that predicate.
- `/services/[slug]` — adopted in the Service-Detail-Page initiative. The route
  reads `services` data, filters with a new `hasCompleteDetailContent` type
  guard, and renders an 8-section composition.

Both routes were designed independently. They converged on the same shape on
most surfaces (`getStaticPaths` over a typed domain collection; one type-guard
predicate per domain co-located with the data; a co-located `<domain>DetailHref`
route helper next to the data; `Breadcrumb` primitive at the top of the page;
canonical URL via Astro's defaults from `Astro.site` and `Astro.url.pathname`).
They diverge cleanly on per-domain content shape (success stories carry
narrative blocks plus before/after images; services carry chips, expanded
features, FAQ, pricing) and on the underlying data-module shape (`services`
follows the ADR-0017 const-Record form; `successStories` is a plain
`readonly SuccessStory[]`).

Two further dynamic detail routes are anticipated:

- **Coach detail** (`/coaches/[slug]`) — coach profiles are currently rendered
  as in-page modals from `~/data/coaches`, with a planned migration to a dynamic
  detail route in the same shape.
- **Legacy success-stories revision** — when the existing route is next touched.

Without an explicit pattern, the third consumer would either fork arbitrarily or
copy whichever of the two existing routes its author opens first. The recurring
decisions (predicate location, route-helper location, back-link primitive,
canonical URL handling, JSON-LD strategy, hash-anchored back-navigation,
module-script footprint) deserve a single named contract.

### Decision drivers

- **One route is a precedent; two are a pattern.** Each new dynamic detail route
  should converge on the same shape unless the divergence is a documented domain
  difference (image-heavy vs. text-heavy, before/after vs. chips), not an
  undocumented wandering of preferences.
- **Code-level safety over reviewer discipline.** The pattern's invariants
  (static paths, type-guarded predicates, additive JSON-LD) must be enforceable
  at the type system or test layer where possible — consistent with ADR-0017
  (compile-time data integrity), ADR-0034 (extract-first), and ADR-0037 (typed
  component tests).
- **Critical Rule 1 honoured by co-located helpers, not by `routes.ts` growth.**
  Detail routes are derived URLs (`<base>/<id>` or `<base>/<slug>`); the
  derivation belongs next to the domain that owns the identifier, not in
  `routes.ts` (which stays a pure path dictionary).
- **Retroactive coverage where it costs nothing.** The existing
  `success-stories/[slug]` route already conforms to the pattern. The ADR
  documents the conformance rather than requiring a delta PR.

### Evaluated alternatives

1. **No pattern — let each route invent its own shape.** Rejected. The consumers
   identified above will multiply the divergence and grow the test surface
   without proportionate benefit.
2. **Wait for a third dynamic route before extracting the pattern.** Rejected.
   The pattern is observable today across two consumers; the third will land
   within months on the upcoming-features list. Late extraction means the third
   consumer ships first and the pattern is then back-fitted under deadline
   pressure.
3. **One ADR per concern (back-link convention; JSON-LD strategy; launch-gate
   location; canonical URL).** Rejected. The concerns are tightly coupled — the
   same page is the consumer of all of them — and splitting them produces four
   ADRs that each describe one face of the same elephant.
4. **One ADR for the consolidated pattern, retroactively covering the existing
   route.** **Chosen.**

## Decision

Every dynamic detail route in the project (`/services/[slug]`,
`/success-stories/[slug]`, and any future addition such as `/coaches/[slug]`)
follows the **dynamic detail route pattern** described below.

### 1. Static path generation over a typed domain collection

Each detail route exports `getStaticPaths` that filters a typed domain
collection (`services`, `successStories`, …) through the launch-gate predicate
(§2 below) and emits one route per qualifying entry. Routes are statically
generated by default per ADR-0022 — `prerender = false` is not used.

The detail route's slug parameter matches a stable identifier on the domain
entry: `service.id` for services, `story.slug` for success stories. The shape is
`{ params: { slug: <identifier> }, props: { entity } }` so the `[slug].astro`
page consumes a strongly-typed `Astro.props.<entity>` directly without a second
lookup.

The function may be defined directly in the page module or imported from a
co-located helper and re-exported (`export { x as getStaticPaths } from '…'`) —
Astro's routing contract checks the module's `getStaticPaths` export, so both
shapes are equivalent. The re-exported-helper shape is preferred when the
route's `getStaticPaths` logic warrants a unit test, because Astro 6 routes any
`.ts` file inside `src/pages/` as an endpoint — a `*.test.ts` next to the page
module would crash the build, so the testable logic must live outside
`src/pages/` and be re-exported into it. `/services/[slug]` follows this shape:
`getServiceSlugPaths` lives in `src/utils/serviceSlugPaths.ts` with a sibling
test, and the page module re-exports it as `getStaticPaths`.

**Preferred shape — ADR-0017 const-Record.** New domain modules adopt the
ADR-0017 pattern (one ID const + ID-keyed `as const satisfies Record<…>`

- derived array). `~/data/services.ts` is the reference shape today
  (`servicesById` at line 202–572, `services` array derived at line 578). This
  form gives compile-time safety on ID lookups and a single source of truth for
  ordering.

**Acceptable shape — typed array module without an ID-keyed Record.**
`~/data/successStories.ts` ships a `readonly SuccessStory[]` array (line 188)
without a `successStoryIds`/`successStoriesById` pair. The detail-route pattern
still applies: `getStaticPaths` filters the array through `hasDetailPage` and
emits one route per qualifying story. The ADR-0017 lift is a separate strand and
not a precondition for the dynamic-detail-route pattern.

When a new domain module is added (e.g., `~/data/coaches.ts` for the upcoming
`/coaches/[slug]` route), authors **prefer the ADR-0017 const-Record form**.
Migration of the legacy `successStories.ts` to ID-keyed shape is its own piece
of work, separate from this ADR.

### 2. Launch-gate predicate co-located with the data

Each domain that has _partially populated_ entries (entries that exist in the
catalog but are not yet ready for a detail page) exports a type-guard predicate
as a named export from its data module:

- `~/data/services` exports
  `hasCompleteDetailContent(service): service is ServiceWithCompleteDetailContent`.
  Threshold: `lead` set, `detailedFeatures.length >= 3`, `fitFor.length >= 3`,
  `faq.length >= 3`. See ADR-0045 for the rationale of dropping the previously
  listed `notFitFor` threshold.
- `~/data/successStories` exports
  `hasDetailPage(story): story is StoryWithDetail`. Threshold: `slug`, `age`,
  and `detail` all defined.

The predicate is _the_ gate. `getStaticPaths` calls it; the type guard narrows
the entry shape in the page module. Other consumers (e.g., `ServiceCard`'s
decision whether to point at the detail page or stay on the contact-form
deep-link) call the same predicate. The predicate is **not duplicated** at any
consumer site.

The predicate's threshold is tuned per domain by the owner. The contract encoded
by the ADR is **its existence and location**, not its specific values.

### 3. Route helper co-located with the data (`<domain>DetailHref`)

Detail-route URLs are reconstructed for navigation through a co-located helper,
not through `routes.ts`. Each domain that ships a detail route exports a pure
function next to its data:

- `~/data/services.ts:605` exports `serviceDetailHref(id: ServiceId): string`
  returning `${routes.services}/${id}`. The JSDoc on this function (line
  595–604) is the canonical rationale: _"Lives next to the data rather than in
  routes.ts because the derivation belongs with the domain — routes.ts stays a
  pure path dictionary, and future detail-route helpers (`coachDetailHref`,
  `successStoryDetailHref`) can follow the same co-location pattern without
  growing routes.ts into a method bag."_
- `~/data/successStories.ts:318` exports
  `successStoryDetailHref(slug: string): string` returning
  `${routes.successStories}/${slug}`. JSDoc cross-references `serviceDetailHref`
  as the established pattern.

This convention is **load-bearing for Critical Rule 1** ("All internal URLs go
through `src/data/routes.ts`"): the rule is satisfied _indirectly_ through these
helpers. Consumers (cards, breadcrumbs, schemas, navigation) call the helper
rather than constructing a path literal. `routes.ts` remains a pure path
dictionary; the domain modules own the detail-route derivation.

Future detail routes (`/coaches/[slug]` and beyond) **must** export a
`<domain>DetailHref` helper next to their data and **must** be consumed from
every linker (cards, breadcrumbs, schema-org `url` fields). A new detail route
that hard-codes `${routes.coaches}/${id}` at any consumer site, or that adds a
route to `routes.ts` instead of co-locating the helper, violates this
convention.

### 4. Back-link via the `Breadcrumb` primitive

Detail pages render `~/components/navigation/Breadcrumb.astro` at the top, above
the page's first content section. The primitive encapsulates:

- `<nav aria-label="Breadcrumb">` landmark
- chevron-separated trail items
- `aria-current="page"` on the current item
- header-clearance (`pt-28` today; encoded once inside the primitive so Header
  height changes are a one-file edit)

The trail's intermediate hrefs **may carry hash fragments** — the component does
not constrain them. Each detail route picks its back-target shape:

- `/services/[slug]` uses
  `trail=[{ label: 'Services', href: routes.services + '#' + service.category }]`
  to drop the visitor back at the right category in the index filter. The
  services-index controller resolves the `#<category>` fragment via its existing
  deep-link path (`servicesFilterController.resolveDeepLink`). _The services
  detail route is the **first consumer of a fragmented `trail[].href`** in this
  primitive — the field's `string` type already permits it; this ADR documents
  the first usage so future Breadcrumb consumers know the shape is supported and
  stable._
- `/success-stories/[slug]` uses
  `trail=[{ label: 'Success Stories', href: routes.successStories }]` with no
  fragment — the success-stories index does not maintain per-tag deep-links
  today. If it ever does, the trail href adds the fragment without a primitive
  change.

Inline `<a>` back-links are **not used**. If a detail route has no trail-shaped
back-navigation (single-step "back to root"), it still uses `Breadcrumb` with a
one-item trail — the landmark + clearance + a11y encapsulation outweigh the
small visual difference.

### 5. Canonical URL via Astro's defaults

Pages do not pass an explicit `canonicalURL` to `BaseLayout`. The default in
`~/components/layout/SEO.astro` already constructs
`new URL(Astro.url.pathname, Astro.site)`. Detail pages let that default hold.
Override only if a future route needs a non-trivial canonical (none do today).

### 6. JSON-LD strategy: additive, never replacing

The base SEO layer always emits a `WebPage` (or `WebSite` on the homepage)
JSON-LD block. Per-page schemas (`Service`, `Person`, etc.) are **appended** via
the optional `additionalJsonLd?: readonly Record<string, unknown>[]` prop on
`BaseLayout` / `BaseHead` / `SEO`. The base block remains unconditional; the
additional blocks are appended after, in caller-supplied order.

Each entry is rendered as
`<script is:inline type="application/ld+json" set:html={JSON.stringify(entry)} />`,
byte-pattern-identical to the existing base block in `SEO.astro`. `is:inline` is
required so Astro does not hoist or bundle the block; `set:html` is required so
the JSON content is not HTML-escaped.

Detail routes build their per-page schema with a pure-function helper co-located
with the domain data (`buildServiceSchema` next to `buildServiceListSchema` in
`~/utils/serviceSchema.ts`; future `buildSuccessStorySchema` would live in
`~/utils/successStorySchema.ts`). Helpers take all external inputs as parameters
— they do not couple to `siteConfig` or `Astro.site` directly.

CSP implications are handled by ADR-0030's post-build hash collector, which
scans `dist/**/*.html` for every `<script type="application/ld+json">` block.
The `additionalJsonLd` mechanism produces standard inline script tags that the
collector picks up automatically. ADR-0030's "Skip rules" section excludes
`application/ld+json` from the strict hash-list anyway, so no per-PR
`netlify.toml` edit is expected.

### 7. Module-script footprint: zero at the page level

Detail pages ship no page-level `<script>` block. All interactive primitives
(Accordion via `<el-disclosure>`, modal triggers via the Invokers API, pricing
toggles via CSS `:has()`, modal mounts via `QuizModal`'s internal script) own
their own bootstrap — typically via `bootstrapOnLoad` per ADR-0026, idempotent
via `data-initialized` guards.

If a future detail route needs page-specific client-side logic, it follows
ADR-0020 (module script default) and ADR-0026 (`bootstrapOnLoad` for cold-load +
view-transition coverage). `is:inline` is reserved for Critical Early Execution
per ADR-0020 and is not expected on detail routes (no flash mitigation needed
because the page contains no filter/toggle that defaults to a different state on
deep-link entry).

### 8. Hash-based back-navigation contract with the catalog controller

When a detail route's back-link points at a hash fragment of its catalog page
(e.g., `/services#bodybuilding`), the catalog controller is expected to resolve
that fragment on hard navigation. Today this contract is satisfied by
`servicesFilterController` (resolves both `#<category>` and `#<service-id>` via
`resolveDeepLink`). Future filterable catalogs that want hash-anchored
back-navigation must implement an equivalent resolver.

The detail route itself is a passive consumer of this contract — it emits a hash
fragment and trusts the catalog to do the right thing on arrival. View
Transition navigation re-fires the catalog controller's bootstrap (ADR-0026) so
the fragment is resolved on every nav path, hard and soft.

## Consequences

### Positive

- **Two routes share one shape.** A reader of `/services/[slug]` sees the same
  architecture as `/success-stories/[slug]`: typed domain collection → predicate
  → co-located route helper → `getStaticPaths` → Breadcrumb → typed sections →
  optional additive JSON-LD → no page-level scripts.
- **Predicate consumers do not duplicate the gate.** The upcoming `ServiceCard`
  link-target switch will import `hasCompleteDetailContent` from
  `~/data/services` rather than re-implement the threshold, just as the
  success-stories card pattern (`SuccessStoryGridCard`) reads `hasDetailPage` to
  decide whether to render a card link.
- **Critical Rule 1 stays clean.** `routes.ts` does not grow per detail route;
  the `<domain>DetailHref` helpers absorb the per-domain derivation next to the
  data they describe.
- **Breadcrumb is the single source of truth for header clearance.** When the
  Header height changes, `Breadcrumb.astro`'s `pt-28` is the one edit. Detail
  routes inherit it.
- **JSON-LD plumbing is uniform.** Every detail route extends the same
  `additionalJsonLd` prop chain. Future routes do not invent a second
  inline-script-injection mechanism.
- **The third consumer's design phase shrinks.** A future `/coaches/[slug]` task
  starts from this ADR and inherits all eight decisions — only domain-specific
  shape (which fields make up the Hero, what schema.org type the JSON-LD uses)
  needs design.

### Negative

- **The pattern hard-codes the `Breadcrumb` choice.** If a future detail route
  has product reasons to use a different back-navigation shape (e.g., a
  side-rail "back to gallery" treatment), the route either conforms to the
  pattern (loses the visual distinction) or supersedes this ADR with a
  successor. Accepted: forking the back-link convention has been considered and
  rejected for both existing routes; if a product reason to fork emerges, it is
  worth a new ADR.
- **The `additionalJsonLd` prop chain grows three layers (BaseLayout → BaseHead
  → SEO).** Each layer is a one-line forward, but the surface is real. Accepted:
  the alternative (page-level inline script tags outside the layout) breaks the
  document-head abstraction and produces inconsistent script locations across
  routes.
- **Two acceptable data-module shapes (const-Record vs. plain typed array) is a
  soft inconsistency.** A reader of two domain modules sees two shapes.
  Accepted: forcing immediate migration of `successStories.ts` to ID-keyed form
  is out of scope for this ADR; the const-Record form is named as the preferred
  shape for new modules, and the array form is bracketed as legacy. The dynamic-
  detail-route pattern itself is shape-neutral (it consumes whatever array the
  module exports).

| Launch-gate predicate co-located               | Yes — `hasDetailPage` type guard exported from `~/data/successStories`                                                                                                                                |
| Co-located route helper (`<domain>DetailHref`) | Yes — `successStoryDetailHref` exported from `~/data/successStories.ts:318`; JSDoc cross-references the `serviceDetailHref` rationale                                                                 |
| Back-link via `Breadcrumb`                     | Yes — `Breadcrumb` rendered at the top of the page with one-item trail                                                                                                                                |
| Canonical URL via Astro defaults               | Yes — page passes no explicit `canonicalURL`; `SEO.astro` default applies                                                                                                                             |
| Additive JSON-LD via `additionalJsonLd`        | Compatible — the route does not currently emit per-page JSON-LD beyond the base `WebPage`. The optional prop is unused today.                                                                         |

**No delta PR required.** The existing route already conforms to the pattern's
invariants. ADR-0038 documents the conformance retroactively without changing
any code in `/success-stories/[slug]`.

If, in a future revision, the success-stories detail route adopts a per-page
JSON-LD schema or hash-anchored back-link, it consumes the same mechanisms
documented here.

## Alternatives considered

- **Keeping two divergent patterns** — rejected, see Decision drivers.
- **Waiting for a third dynamic route before extracting the pattern** —
  rejected. Premature extraction is a documented anti-pattern under ADR-0034's
  rationale, but two consumers already exist; this ADR _describes_ an existing
  convergence, it does not invent abstraction ahead of evidence.
- **One ADR per concern** — rejected. The concerns are coupled at the page
  level; splitting produces four ADRs with overlapping contexts.
- **Per-domain ADR (one for services-detail, one for success-stories- detail)**
  — rejected. The point of an ADR is to lift the recurring decision out of the
  per-feature noise; per-domain ADRs would defeat that.
- **Add detail-route paths to `routes.ts` instead of co-locating the
  `<domain>DetailHref` helpers** — rejected. `routes.ts` is a pure path
  dictionary today; turning it into a method bag with one function per detail
  route per domain conflates the static path table with per-domain derivation
  logic. The `serviceDetailHref` JSDoc captures the rationale at the call site
  (cf. §3 above).
